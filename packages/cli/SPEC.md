# `@zmdb/cli` — the single `zmdb` executable SPEC

> Status: **FROZEN** for GitHub sub-issue #626. This specification creates no executable or manifest change.

## 1. One command product

`@zmdb/cli` owns the only executable in the project:

```json
{
  "bin": {
    "zmdb": "./src/bin.ts"
  }
}
```

Installing `@zmdb/cli` directly or installing `zmdb` makes that one executable available. The target removes `zmdb-codegen`; no alias, forwarding script or second bin entry is permitted. #721/#728 own
the coordinated version in which that removal occurs.

Twenty current shipped/build-input files move to this package. The exact paths are frozen in
[`../../.github/scripts/verify-tooling-ownership.SPEC.md`](../../.github/scripts/verify-tooling-ownership.SPEC.md). Reusable compiler and schema-lifecycle operations move to their libraries instead of
being copied here.

## 2. Dependency and loading boundary

Required edges:

```text
@zmdb/compiler ─┐
                ├──> @zmdb/cli
@zmdb/migrations┘
```

The package root and binary may eagerly import only Node built-ins, `@zmdb/compiler`, `@zmdb/migrations` and CLI-local argument/output code. Application-framework commands are loaded after argument
parsing:

| Command              | Dynamic requirement                                            |
| -------------------- | -------------------------------------------------------------- |
| `modules`, `repl`    | the public application/module/devtools contracts               |
| `studio`             | web, schema and database runtime contracts                     |
| `client generate`    | the public HTTP-contract compiler                              |
| future optional verb | one named public package contract, never a private source path |

`esbuild` and application-framework packages are optional peers used only by those command modules. A missing optional peer exits 2 and names both the command and installable package. Help, version,
codegen and migration commands remain usable without those peers.

No command is registered by import side effect. A literal command table maps a verb to one lazy loader, and loading one verb does not evaluate another.

## 3. Public API and process contract

The package has one public library entry:

```ts
export interface CliEnvironment {
  readonly cwd?: string;
  readonly stdinIsTTY?: boolean;
  readonly input?: NodeJS.ReadableStream;
  readonly output?: NodeJS.WritableStream;
  readonly stdout?: (text: string) => void;
  readonly stderr?: (text: string) => void;
  readonly environment?: Readonly<Record<string, string | undefined>>;
  readonly homeDirectory?: string;
}

export declare function runCli(argv: readonly string[], env?: CliEnvironment): Promise<number>;
```

Exit codes remain:

- `0`: requested operation completed or a read-only result contains no error finding;
- `1`: the invocation was valid but the operation failed, found drift, or `--check` found stale output;
- `2`: invalid arguments, unresolved config, unavailable optional command or refused interaction.

Human output and the one-document `--json` contract remain frozen by the existing CLI SPEC. The bin does only:

```ts
process.exitCode = await runCli(process.argv.slice(2));
```

Every command can be tested through `runCli` with injected streams; no test needs to mutate `process.argv` or spawn the executable unless it is specifically proving installed-bin behavior.

## 4. Command ownership

| Command                            | Delegated operation                                                    |
| ---------------------------------- | ---------------------------------------------------------------------- |
| `codegen [--check] [--watch]`      | `@zmdb/compiler` project compilation and artifact writer               |
| `generate`, `embed`, `export`      | `@zmdb/migrations` library operations                                  |
| `migrate`, `rollback`, `status`    | `@zmdb/migrations/runner`                                              |
| `push`, `check`, `upgrade`, `pull` | `@zmdb/migrations` library operations                                  |
| `new`                              | CLI-owned scaffolding and templates                                    |
| `modules`, `repl`, `studio`        | CLI-owned presentation over dynamically loaded public application APIs |
| `client generate`                  | dynamically loaded HTTP-contract compiler                              |

The CLI parses arguments, loads config, requests confirmation and renders output. It does not own a second reflector, diff engine, migration parser, catalog parser, declaration emitter or database
runner.

`codegen` is the exact replacement for `zmdb-codegen`. It keeps `--project`, `--config`, `--check` and `--watch`; conflicting finite/watch flags are refused with exit 2. The generated bytes and
one-session behavior come from `@zmdb/compiler`.

## 5. Config and facade

The CLI imports `loadConfig` from `@zmdb/compiler/config`. It does not publish its own config subpath. The product package preserves `zmdb/config` as an identity facade over the compiler subpath.

`zmdb/cli` remains the stable product entry and re-exports `runCli` and its public result/error types by identity from `@zmdb/cli`. Advanced consumers may import the implementation package directly.
Installing `zmdb` depends on `@zmdb/cli`, which is how the product install exposes the bin without making the facade own its implementation.

## 6. Packed-consumer evidence

The packed CLI consumer installs `@zmdb/cli`, `@zmdb/compiler`, `@zmdb/migrations` and required peers from tarballs outside the workspace. It proves:

1. exactly one `node_modules/.bin/zmdb` resolves to the CLI package;
2. `zmdb --version`, help and an invalid invocation obey stdout/stderr/exit rules;
3. `zmdb codegen --check` reaches the compiler package and never `zmdb-codegen`;
4. a migration command delegates to the migrations package;
5. help and database commands work with optional application peers absent;
6. selecting an optional command with its peer absent produces the frozen exit-2 diagnostic; and
7. no packed file imports `packages/*/src` or an old implementation-owner tooling subpath.

## 7. Non-goals

- No general command framework, plugin registry or global command registration.
- No compatibility executable; `zmdb/cli` is a stable product facade, not a second implementation.
- No runtime package imports the CLI.
- No command hides a compiler, migration or application operation that cannot be called as a library.

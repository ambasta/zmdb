Where we don't win — gaps & design trade-offs (honest)

We do not win every case in every runtime. This table is generated from the same matrix above: for each runtime × case it shows zmdb-aot's rank and, when behind, the leader and the gap. Below it, each recurring gap is explained — separating fixable deficiencies from deliberate design trade-offs.

Validation trade-offs

  • Parse cases vs typia (~1.0–1.2× on Node/Deno). typia edges the parse variants because its generated object-rebuild is marginally leaner than ours. The gap is small and swings run-to-run under machine load; our is-check itself is byte-for-byte the same straight-line inline typia emits. This is a fixable micro-gap, not a design limit — tracked as a perf issue.
  • assertLoose vs TypeBox-JIT on Node (~1.13×). TypeBox compiles with new Function() at runtime; its JIT'd closure has a tiny edge over our module-level function on the pure loose path. Trade-off: we emit static, tree-shakeable, source-visible code at build time (no runtime eval/new Function, CSP-safe) — we accept a few percent on this one case to keep that property.
  • Strict (excess-key) cases top out ~40–55M ops/s. Rejecting excess keys requires enumerating the object's own keys (for-in count). That is an inherent cost of "no extra properties" when the instance shape isn't known until runtime; typia sits in the same band (and we lead Node assertStrict). This is a property-of-the-problem, not a zmdb deficiency.
  • Deno strict/loose look lower in the harness. An isolated micro-probe puts our Deno strict at ~40–55M (competitive with typia), but the moltar runner reports less — a Deno warmup/sampling artifact, the same class of caveat as Bun's dead-code-elimination below. Flagged, not claimed.
  • Bun assertLoose = 1.06B ops/s is not real. Bun's JIT dead-code-eliminates the no-op loose body. We surface the number but do not claim it.
  • The shipped default is the runtime path. Without the AOT transform wired in, zmdb (runtime) loses to zod v4 on most cases. The headline numbers require the build plugin — a deliberate "opt-in for peak, correct-by-default" stance.

ORM trade-off — tail latency

zmdb leads throughput (2,491 req/s) and median p50 (112ms) but has the worst tail (p90 220ms / p95 256ms vs drizzle 188/207). Root cause is by design: zmdb has no identity map, no statement cache, and no prepared-statement reuse — every request compiles and executes fresh. That keeps the common path lean (great average/median) but adds variance under load spikes (worse tail). Adding a prepared-statement/plan cache would improve the tail at the cost of the zero-state, no-hidden-cache guarantee. This is the central zmdb trade-off: predictable, stateless, zero-overhead-per-call in exchange for a fatter tail than ORMs that keep server-side caches. See Anti-patterns for why the caches are excluded.

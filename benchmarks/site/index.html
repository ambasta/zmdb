Where we don't win — gaps & design trade-offs (honest)

We do not win every case in every runtime. This table is generated from the same matrix above: for each runtime × case it shows zmdb-aot's rank and, when behind, the leader and the gap. Below it, each recurring gap is explained — separating fixable deficiencies from deliberate design trade-offs.

Validation trade-offs

  • Fixed: parse no longer rebuilds the object. The parse case used to allocate a fresh result object; the shipped parse<T> contract returns the validated input as-is (no transform/coercion for a plain structural type — same as typia's assertParse). A low-noise probe measured this at 153M vs 98M ops/s (1.56×). After the fix Node leads parseStrict/assertLoose/assertStrict and Deno leads all four cases; Node parseSafe is within ~1.05× of typia (run-to-run noise).
  • parse vs typia is now noise-level. Our is-check is byte-identical to typia's inline; after removing the rebuild the two trade the parse/strict lead run-to-run on a shared box. No structural gap remains — see the fixable-item issue #162.
  • assertLoose is NOT a real gap. We measured our single boolean-chain is() at 352M ops/s — faster than new Function() JIT (124M), early-return (126M) and hoisted (89M) variants. Our static, source-visible, CSP-safe emission already beats the JIT approach; the earlier "1.13× behind TypeBox-JIT" was harness/wrapper measurement noise, now reclassified.
  • Strict (excess-key) cost ~40–60M is a property of the problem. Rejecting excess keys must enumerate own keys (inlined for-in with early-exit — no helper call, no Object.keys() allocation). typia sits in the same band; we lead Node/Deno strict.
  • Bun strict favours typia (~2.4×). On Bun's JIT specifically, typia's strict emission wins the two strict cases — the same Bun JIT that dead-code-eliminates our no-op assertLoose (942M, not real). Runtime-specific JIT behaviour, flagged, not a portable gap (Node and Deno both lead strict).
  • The shipped default is the runtime path. Without the AOT transform wired in, zmdb (runtime) loses to zod v4 on most cases. Peak numbers require the build plugin — a deliberate "opt-in for peak, correct-by-default" stance.

ORM trade-off — tail latency

On the re-run (real Northwind, 427k-request replay), zmdb leads throughput (2,916 req/s) and average (102ms); drizzle keeps the best tail (p95 173.8 vs zmdb 215.5). We investigated the cause: the per-request query compile is ~254ns — negligible against a ~100ms round-trip — so the tail is round-trip + pool contention + GC variance under load, inherent to the stateless, no-identity-map, no-hidden-cache design. We then empirically tested the real lever: ZMDB_PREPARED=1 (server-side prepared statements) reproducibly lifts zmdb to 3,068 req/s / 97ms avg and cuts the tail by ~11ms p90 / ~10ms p95 (see the head-to-head table above). So the tail can be improved — we keep it an explicit opt-in rather than a hidden cache, preserving the zero-state guarantee by default. drizzle still owns the tail; that remains an honest trade-off.

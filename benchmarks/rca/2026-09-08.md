# Performance investigation — 8 September 2026

Measured product revision: `07b3ec8019360ca7f23827379047831d69da0055`.

The goal is faster real application work while retaining TypeScript declarations as the source of truth. This investigation changes benchmark code and an isolated database; it does not ship the
experimental product changes.

## Measurement conditions

The machine is an AMD Ryzen 7 7840U laptop with eight physical cores and 16 logical CPUs. Node is 26.8.1, Bun 1.4.0, Deno 2.9.6 and TypeScript 7.0.2. PostgreSQL is 18.6, the current stable release,
with its default durability settings enabled. The disposable server uses image digest `sha256:4ef4dbc939d61acea57712655ddb4b4ab27419c913f94cca0cd57cb3ea3c2280`.
[PostgreSQL release notes](https://www.postgresql.org/docs/release/18.6/).

Each application uses one process on logical CPU 4. PostgreSQL uses CPUs 6–11; its HTTP replay client uses 12–15. The HTTP-only client uses CPUs 10, 12 and 14 while PostgreSQL is idle. Timed campaigns
run sequentially; source preparation runs in parallel. The final comparison runs have no concurrent owned compiler work. Ordinary desktop services remain running, so sample ranges matter. The initial
exploratory pool-size sweep overlapped some compiler preparation and is not the basis of a precise performance ranking. The later index experiment was repeated after setup finished, in reversed order.

The comparator set targets fast JavaScript implementations: Fastify on Node, Elysia on Bun, Hono on Deno, Drizzle/Kysely over the same PostgreSQL driver, and Typia/TypeBox/Ajv for generated
validation. Native HTTP, pg and JSON operations provide lower-overhead reference points, not equivalent full frameworks. No single framework leads all hardware, runtimes, payloads and database
workloads.

Raw samples, profiles, generated sources and exact dependency locks are retained outside the checkout in the companion `benchmark-20260908` evidence directory. The small runners in this directory are
standalone experiments, not CI gates.

## PostgreSQL tail latency: missing search indexes dominate the old replay

The historical 13-route HTTP fixture is Hono plus SQL builders, not the public repository. It is also unsuitable for a fair old Drizzle ranking: its Drizzle customer schema selects two fields while
zmdb/Kysely select all columns, and some join responses have different structures. The new repository comparison uses matched outputs instead.

The replay's full-text searches recompute `to_tsvector` over every product or customer row. Its seed creates foreign-key lookup indexes but no corresponding search indexes. Those two searches account
for **99.24% of captured PostgreSQL statement execution time** before indexing. The recorded searches return no rows, so these results specifically include expensive negative full-text lookups.

The controlled experiment changes only two expression GIN indexes, keeping the same application, request replay, pool of 12 and 400 concurrent clients. Each sample follows five seconds of warmup and
measures 15 seconds. Order is unindexed/indexed/indexed/unindexed. All four samples have zero HTTP errors. **This is zmdb versus itself, not a framework ranking. No competitor is compared against an
indexed zmdb query while using unindexed tables.**

| Database state             | Requests/second, both runs | HTTP p99, both runs |
| -------------------------- | -------------------------- | ------------------- |
| Existing unindexed fixture | 2,952 / 2,678              | 183.5 / 202.4 ms    |
| Matching search indexes    | 15,673 / 15,287            | 48.4 / 48.8 ms      |

The matched-pair throughput improvement is 5.3–5.7 times. Query plans change from sequential scans to bitmap index scans. Representative unloaded search execution times change from 14.435/7.757 ms to
0.030/0.027 ms. These plan timings are examples, not percentile estimates.

A separate instrumented pass records mean pool wait of 92.61 ms and query roundtrip of 4.43 ms before indexing, versus 17.17 ms and 0.93 ms after indexing. Those spans include warmup; roundtrip
includes network, database work, decoding and JavaScript scheduling. They are not per-request server-only timings, and their percentiles must not be added. The diagnostic CPU profile is mostly idle
before indexing. Instrumentation allocates its own span arrays, so its GC samples are not used to blame production allocations.

**Change:** make the benchmark's search indexes match its queries, then use the same index definitions for every compared ORM. Keep search configuration and index expressions tied to the typed
schema/migration definitions. Existing SQL schema objects already support expression indexes and `method: 'gin'`; this is not a reason to invent another schema system. GIN is PostgreSQL's preferred
text-search index type. [PostgreSQL text-search indexes](https://www.postgresql.org/docs/current/textsearch-indexes.html).

Larger pools alone are not the fix: the exploratory pool-48 runs made tails worse than pool-12 without increasing throughput. At saturation, admitting more work mainly adds waiting. Optimize the query
plan first, then measure pool size and admission at the intended throughput.

## Generated validation and serialization

These operations use one shared reflected TypeScript model. The exact versions are Typia 14.0.5, TypeBox 1.3.29, Ajv 8.20.0 and fast-json-stringify 7.0.1. Both zmdb and Typia use actual compiler
output. Competitor schemas are derived from the same reflected model. Results consume rotating inputs and outputs.

The model contains seven root and three nested fields, including four bounded numbers. It has no arrays, optional fields, unions or formats. Boolean APIs do not coerce, copy, default or mutate. Ajv's
normal error bookkeeping remains enabled. Values below are median nanoseconds per operation across five samples; they include loop/checksum costs and are not individual-call latency percentiles.

| Operation              |  zmdb | Typia | TypeBox |   Ajv |
| ---------------------- | ----: | ----: | ------: | ----: |
| Loose valid            | 17.40 | 15.04 |   20.17 | 22.78 |
| Loose late invalid     | 17.40 | 14.99 |   20.73 | 30.37 |
| Strict valid           | 27.59 | 33.08 |   38.42 | 38.21 |
| Strict excess property | 27.35 | 41.87 |   36.58 | 45.63 |

zmdb already leads these strict cases. Its loose validation deficit is small relative to the larger gaps below. Removing four redundant NaN checks from the generated bounded-number predicates reduces
valid-case time by 6–11% in a separate paired run. This is a compiler optimization opportunity: only omit a predicate when the remaining generated checks imply it. Do not weaken general number
validation.

| Serialization of valid exact-shape inputs | zmdb runtime | Typia AOT | fast-json-stringify | Native JSON |
| ----------------------------------------- | -----------: | --------: | ------------------: | ----------: |
| Plain strings                             |    833.82 ns | 477.52 ns |           498.02 ns |   368.97 ns |
| Escaped/Unicode strings                   |  1,052.26 ns | 774.04 ns |           810.02 ns |   520.47 ns |

The public zmdb serializer currently uses `JSON.stringify` with a replacer to check nested bigint values. Removing just that argument reduces measured time by 50–55%, with identical bytes for every
tested input. The CPU profile locates the work in the serializer but cannot alone separate callback dispatch from native fast-path eligibility. V8 explicitly documents that supplying a replacer
disables its fast serializer. [V8 JSON.stringify implementation](https://v8.dev/blog/json-stringify).

**Change:** let compile-time type information select the native JSON fast path for suitable data and generate specialized handling only where required. Native JSON beats both generated serializers on
this model, so blanket string concatenation generation is not supported by these results. Preserve the public bigint, error, property and `toJSON` contracts; the prototype only establishes equivalence
for ordinary JSON-safe data with unmodified built-ins.

Source owners are `packages/validator/src/serialization/index.ts` and `packages/compiler/src/emit/index.ts`. No production changes from these experiments have been integrated.

## HTTP: the larger framework gap is the Fetch adapter

The public decorated router and adapters serve the zmdb cases. Every candidate uses the same generated body validator and returns the same body bytes. The two workloads are `GET /user/42` and a small
validated `POST /user`; they measure dynamic routes rather than a prebuilt constant response. Fastify is 5.12.3, Elysia 1.4.30 and Hono 4.13.7. These are fast comparators chosen for their target
runtimes, not a claim that one is the universal industry leader.

Each cell has three rotated samples of eight seconds after two seconds of warmup, using oha 1.16.0, HTTP/1.1, keepalive and 64 connections. All 48 samples completed without HTTP/load errors.
Throughput is maximum closed-loop throughput; the latency distributions are not corrected for coordinated omission and do not establish a fixed-arrival-rate service-level objective.

| Runtime/workload    | zmdb requests/s | Comparator requests/s | zmdb p99 | Comparator p99 |
| ------------------- | --------------: | --------------------: | -------: | -------------: |
| Node parameter      |          79,435 |        Fastify 89,739 |  1.51 ms |        0.98 ms |
| Node validated POST |          61,799 |        Fastify 61,940 |  2.19 ms |        1.41 ms |
| Bun parameter       |         122,317 |        Elysia 211,274 |  0.82 ms |        0.59 ms |
| Bun validated POST  |          55,252 |        Elysia 132,037 |  1.99 ms |        0.89 ms |
| Deno parameter      |         106,576 |          Hono 210,334 |  1.22 ms |        0.39 ms |
| Deno validated POST |          69,780 |          Hono 153,719 |  2.70 ms |        0.50 ms |

Entries are medians of the three throughput values and, separately, the three per-run p99 values. They are not pooled percentiles or necessarily one selected run. The Node parameter case varies
materially: Fastify spans 85,410–112,499 requests/s and zmdb spans 78,345–86,542. Node POST throughput is effectively tied within observed variation. Bun/Deno gaps are substantially larger than their
sample ranges. The compact results file retains all ranges.

On these workloads the public Fetch path constructs a URL, materializes request headers into an object, creates a generic request/context, then converts the generic response back to Fetch headers and
a Response. POST additionally collects stream chunks in JavaScript before parsing. Those are concrete owners to profile; source inspection alone does not assign a percentage of the gap to any one
step.

The Deno POST CPU profile records the Fetch adapter (6.65% of samples), manual body reader (5.07%), Headers construction (5.01%), body-stream getter (3.32%) and header iterator (2.35%) among visible
costs. Idle is 33.35% and GC 6.84%. These are sampled leaf shares across the diagnostic profile, not independent measured speedups, and removing their sum is not a justified forecast.

Replacing manual chunk collection with native `arrayBuffer()` in a separate ABBA experiment does **not** improve this case: baseline throughput is 77,330/75,068 requests/s, versus 71,859/73,638 for
the variant. p99 ranges overlap. That variant also loses early streaming memory-limit enforcement and still touches `request.body` before the native read. It is a rejected production change and does
not rule out every possible native body path.

A second, separate ABBA session also avoids the eager `request.body` getter. The original bounded reader reaches 58,762/57,625 requests/s; the combined variant reaches 66,352/65,636, a 13.4% increase
in mean throughput. Per-run p99 changes from 4.01/4.15 ms to 3.19/3.33 ms. This measures the combined change, not the getter's isolated effect. Its slower baseline is not pooled with the earlier
sessions. The loss of early memory-limit enforcement still makes it unsuitable for production; it is a lead for a safe bounded implementation.

**Direction:** specialize the existing adapters from typed route metadata, retain native request/response representations longer, and materialize context fields only when needed. Preserve body limits,
validation, cancellation, guard order, versioning and error behavior. Prefer native bounded ingestion where a serving runtime provides it. The measured Fetch gap establishes the priority; the exact
gain from a complete specialization still requires implementation and measurement.

## Actual repository and relation loading

This comparison uses PostgreSQL through pg 8.23.0, Drizzle 0.45.2 and Kysely 0.29.5. All candidates use the same database, tables, indexes, driver and pool configuration. Every lane returns the same
fields and values. A lookup returns one row in one query. Nested loading returns 25 users, 100 posts and 300 comments. Raw pg, builders, zmdb's repository and scoped deferred population use three
batched queries. Drizzle's native relational `findMany` is separately measured using its actual one-statement lateral JSON aggregation, rather than forcing it to use the same strategy. Child order is
canonicalized for correctness checks, outside timing.

Three rotated rounds measure concurrency 1 and 48 with the same pool size of 12. Each cell has one second of warmup and four measured seconds: 72 clean cells in total. Here, an operation is a complete
lookup or graph load, not a SQL statement. Per-operation timing-array allocation is included in these clean runs, consistently across lanes. Sorting and JSON writing occur outside the timed interval.
CPU profiles separately omit those arrays, so their allocation is not attributed to the product.

| Lookup, concurrency 48 | Operations/s | Operation p99 |
| ---------------------- | -----------: | ------------: |
| Raw pg                 |       78,096 |       1.24 ms |
| zmdb builder           |       59,034 |       1.39 ms |
| Kysely                 |       49,792 |       1.75 ms |
| zmdb repository        |       49,751 |       1.80 ms |
| Drizzle builder        |       22,425 |       3.59 ms |

| Nested graph                             | Ops/s at concurrency 1 | Ops/s at concurrency 48 | p99 at concurrency 48 |
| ---------------------------------------- | ---------------------: | ----------------------: | --------------------: |
| Raw pg, three queries                    |                  1,945 |                   3,579 |              16.95 ms |
| zmdb builder, three queries              |                  1,867 |                   3,316 |              19.93 ms |
| Kysely, three queries                    |                  1,823 |                   3,183 |              19.31 ms |
| zmdb repository, three queries           |                  1,398 |                   1,808 |              33.33 ms |

These are medians of per-run measurements, not pooled percentiles. At concurrency 48 the repository spans 1,784–2,018 operations/s and native Drizzle relations span 1,864–2,038; their ranges overlap.
zmdb's builder is consistently faster on this graph, but its full repository has substantial additional cost. One query is not automatically the better plan: native aggregation performs more server
work, while select-in loading spends additional roundtrips. The appropriate strategy depends on graph width, cardinality and network latency.

The shared seed has 2,000 users, 8,000 posts and 24,000 comments. Every comparator uses the primary-key indexes and the same `users(tenant_id, id)`, `posts(user_id)` and `comments(post_id)` indexes.
These are separate tables from the Northwind index experiment. Query/result correctness is checked before timing; no candidate gets a private index, smaller projection or precomputed result.

At nested concurrency 48, each lane consumes 97.5–98.8% of one client CPU. PostgreSQL execution averages approximately 0.12 ms per three-query operation versus 0.40 ms for native Drizzle aggregation.
Representative plans use index scans for the three batched reads. In this local workload, additional repository work is primarily a client-side cost, not evidence that PostgreSQL needs a larger pool
or more indexes.

Profiles without per-operation latency arrays identify `childrenByParent` (11.3% self samples), `loaderKey` (4.9%), population attachment (4.8%) and row copying. A separate instrumented trace puts
repeated metadata planning at about 3 microseconds per graph. A plan cache is therefore not the first optimization supported by this workload. Trace instrumentation materially increases latency
(repository p99 61.8 ms versus clean median 33.3 ms); those absolute timings are excluded from the comparison.

An evidence-only numeric scalar-key fast path preserves the existing encoded key and fallback for other types. Four ABBA cells produce 1,939/1,855 operations/s for the canonical implementation and
2,161/2,186 for the prototype: paired gains of 11.5% and 17.8%. Full graph equality and the three-query behavior still pass. This supports reducing key-encoding allocations. It does not establish the
gain for composite/string keys or justify dropping collision protection and row-copy isolation.

**Change:** specialize grouping/key encoding from the existing typed relation and primary-key metadata, then remove redundant intermediate copies where ownership permits. The owners are `loaderKey`,
`childrenByParent` and `populateRows` in `packages/orm/src/index.ts`. Preserve explicit/scoped loading, batched traversal, filter behavior and the fetched row types. Measure a native single-statement
strategy where network latency or fanout justifies it; do not force one strategy on every graph.

## Proposed implementation order

| Priority | Change                                                                  | Evidence and expected scope                                                                                                                                                                                                             |
| -------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1        | Correct the old benchmark's projection parity and shared search indexes | The 5.3–5.7× index result is a database/configuration improvement available to every framework, not a zmdb advantage. Stop publishing unmatched rankings.                                                                               |
| 2        | Select a safe native serialization path using compiler type information | The JSON-safe model's serialization time falls 50–55% in the controlled experiment. Preserve behavior for unsupported values and customized objects.                                                                                    |
| 3        | Specialize Fetch adapters from typed route metadata                     | Bun/Deno HTTP gaps are the largest consistent framework gaps measured here. Avoid unnecessary request/header/context conversion; body limits and all existing route semantics remain required. No complete speedup is yet demonstrated. |
| 4        | Reduce relation-key/grouping/copy allocations                           | The numeric-key prototype improves this nested workload by 11–18%. Further gains from grouping/copy changes remain unmeasured.                                                                                                          |
| 5        | Remove logically redundant generated predicates                         | Bounded-number validation improves 6–11% in the paired microbenchmark. Strict validation already wins these cases.                                                                                                                      |

All proposals retain the existing direction: TypeScript declarations → compiler IR → generated validators, serializers, route execution and schema-aware query code. None requires a second
hand-maintained runtime schema, handwritten per-endpoint validation or hidden property-triggered database I/O.

The evidence supports specific targets, not a promise to lead every category. Runtime ceilings, payload shape, network latency, graph fanout and required semantics change the winner. This campaign
does not measure TLS, multicore HTTP, remote PostgreSQL, other database dialects, ORM on Bun/Deno, wide unions/arrays, large bodies, sustained fixed-arrival SLOs or every third-party ORM/framework.
The short samples on one development laptop establish useful local comparisons and controlled optimization leads; they are not a universal ranking.
